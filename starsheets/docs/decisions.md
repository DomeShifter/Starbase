One line per decision: what, why, what we rejected. Newest first.

| 2026-11-25 | "View as photos" is a third view switch in the Drive (beside Grid and List), remembered per person. It shows a folder as a virtualised grid of square thumbnails from the server's photo index, and a full-screen viewer with a slideshow. The browser decodes the pictures (`createImageBitmap`); the desktop decodes with the `image` crate. Textures have a budget: 96 MB on the web, 256 MB on the desktop, least recently drawn first. The original is fetched only when zooming in past what the 1024 px thumbnail can show, no bigger than the GPU's largest texture. The viewer is black in light and dark mode. | Research (photos-mode.md §4): decoding in WASM is slow and single-threaded, and textures are GPU memory the page must manage itself; one code base for web and desktop | An HTML `<img>` grid (a second UI stack beside egui); decoding in Rust on the web; month headings in the grid (the virtualised grid needs rows of equal height; maybe later) |
| 2026-11-25 | Photos is opt-in per folder: nothing is indexed until someone who may edit a folder turns on "View as photos" for it (`POST /api/photos/enable`, covering the folders inside); its owner can turn it off, which forgets its pictures and deletes their thumbnails at once. GPS goes only to people who may edit through their own account or a named share; index status is for the server's owner only. Pictures are streamed once to hash them and the opened file is handed to the decoding child (no whole picture in the server); 2 workers by default, workers × child memory kept within half of the container's memory limit; the child also gets RLIMIT_NOFILE, no-new-privileges and (where the kernel has it) Landlock with no file access. No inotify on network storage (rescans only); one scanner thread, at most 500 files per index lock. The cache goes to a `/cache` volume when one is mounted, is capped (least recently shown thumbnails go first) and a damaged index is rebuilt | Security review of #53: indexing every person's pictures at start-up without asking went past what anyone chose (and James keeps faces and the like opt-in); a big picture read whole into the server, times several workers, could exhaust a small container | Indexing everything at start-up; one switch for the whole server; inotify on a network share (walks the whole tree over the network and still sees no other computer's changes) |
| 2026-11-25 | Photos job 1 (server): every picture in the store goes into an index (SQLite in `.starsheets/photos-cache`, or STARBASE_PHOTOS_CACHE; schema versioned; rows keep a stable id across renames, for later faces, tags and albums) with its EXIF date, orientation, camera and place. Each picture gets 256 and 1024 px thumbnails, kept by content hash and made by a few low-priority worker threads. Each picture is decoded in a child process (`starsheets-server photo-worker`) with memory, CPU and wall-clock limits, after a header check (at most 30000 px a side, 50 MP, 150 MP for JPEG). Changes are found by inotify, by a stat-only rescan (10 min on a network file system, 1 h on a local disk, STARBASE_PHOTOS_RESCAN) and when a folder is opened. Thumbnails are cached `private, immutable` only when asked for with the picture's content tag `v`, else `private, no-cache`. JPEGs are decoded with jpeg-decoder's scaled DCT. The cache is left out of backups. API: docs/photos-api.md | A network share (such as a NAS share) never tells inotify about other computers' changes, so rescans are needed. Decoding untrusted files in a child process means a decoder crash, hang or memory blow-up costs one picture, not the server. Hash-keyed thumbnails survive renames and copies. An address that names exact bytes can be cached for good without ever showing a stale picture | libjpeg-turbo (`turbojpeg`): measured 98 against 79 thumbnails/s (8 threads, 12 MP), but it needs cmake and nasm in every build, arm64 cross-builds included (revisit with job 5, which brings C libraries anyway); the `image` crate's full JPEG decode (69/s); `Cache-Control: no-store` (each grid scroll would fetch and access-check every thumbnail again); catch_unwind alone (can't stop a decoder that hangs or eats memory); SQLite WAL with shared memory (unreliable on network file systems: the index holds its file exclusively instead) |
| 2026-11-25 | The Drive keeps every kind of file: listed, uploaded (`?as_is=1` keeps the name and type), downloaded, renamed (the type stays), moved, shared and binned like spreadsheets; versions only for Sheets and Docs files; no live room for anything else. Pictures, PDFs, sound, films and text open in a preview (crates/server/src/preview.rs): a script-free page made by the server with a sandbox CSP, media bytes from an allow-list of types with `nosniff` and byte ranges, text escaped into `<pre>`. HTML and SVG are download only. Other files' downloads stream from disk (at most 16 at once per person, 64 in all). Replacing such a file by upload puts the old one in the bin. Symbolic links inside the storage folder are never followed, to files or folders, for security (one made over a file share could reach .starsheets or another person's folder); anyone who relied on symlinked folders must use real folders or bind mounts instead. and reads check the opened file is the one checked. Follow-up: serve PDFs from a separate origin, since a PDF can't be sandboxed (the viewer is a plugin) | A Drive replacement has to hold photos and PDFs; never running a stored file as a page on the app's own site keeps one uploaded file from acting as the person who opens it | SVG shown as `<img>` (safe as an image, but the same file opened directly is a document that can run script, and one missing header would make that live); a separate download domain (more setup for self-hosters) |
| 2026-11-24 | A page left open renews its single sign-on session itself: about 10 minutes before the end (`/api/info` gives `expires_in`) or when a request answers 401 with `"renew": true`, by the same `prompt=none` trip as on loading, back to the same file, only at a quiet moment (nothing unsaved or on its way, no cell being typed, no dialog, 4 s without input).
